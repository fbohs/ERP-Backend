# Database Architecture

> Reference for anyone working on the data layer. Covers the responsibility split between Prisma, Kysely, and raw SQL — and the workflows required for each.

## Overview

The database layer uses **two tools with strictly separated roles**:

| Tool | Role | Never used for |
|---|---|---|
| **Prisma 7** | Schema definition + migrations only | Runtime queries |
| **Kysely 0.29** | All runtime queries (type-safe) | Schema changes |
| **Raw SQL** | GIN indexes, operator classes, anything Prisma DSL cannot express | Business logic |

This separation exists because Prisma 7 moved to a WASM query compiler that runs on the JS main thread. Running Prisma queries under load would compete with the HTTP event loop. Kysely talks directly to `pg` and stays off that path entirely.

## PostgreSQL

- **Version:** 18 (alpine image in development)
- **Dev database:** `erp_dev` at `localhost:5432`
- **Connection:** managed by Kysely via `pg.Pool`, configured in `src/shared/db/`
- **Env file:** `.env.local` (development only — never `.env`)

---

## Prisma

**Only used for:**
- Defining the schema (`prisma/schema.prisma`)
- Generating and applying migrations (`prisma/migrations/`)
- Running Prisma Studio (`npm run db:studio`) for visual inspection

**Never used for runtime queries.** `PrismaClient` is not imported outside `src/shared/db/`.

### Useful commands

```bash
# Generate a new migration (interactive — must run in a real terminal)
npm run db:migrate -- --name <short_imperative_description>

# Generate migration file WITHOUT applying it (add raw SQL before applying)
npm run db:migrate -- --name <name> --create-only

# Apply pending migrations (non-interactive — safe for CI/scripts)
npm run db:migrate:deploy

# Open Prisma Studio
npm run db:studio
```

### Type mapping

Prisma maps `Json` to **PostgreSQL `JSONB`** for PostgreSQL datasources. There is no separate `Jsonb` type in the Prisma DSL. Any `Json` field in `schema.prisma` becomes a `JSONB` column in the database.

---

## Kysely

**Used for all runtime queries.** Configured in `src/shared/db/`. Every repository receives a `Kysely<DB>` or `Transaction<DB>` instance — never `PrismaClient`.

### Type generation

Kysely types are generated by `kysely-codegen` **from the live database**, not from Prisma's schema. This is intentional — the database is the source of truth.

```bash
# Regenerate types after every migration
npm run db:codegen
# Outputs to: src/types/db.ts
```

**This must run after every migration.** CI fails if `src/types/db.ts` is stale.

### Transaction pattern

```typescript
// Service owns the transaction, repositories accept executors
await db.transaction().execute(async (tx) => {
  await productRepo.withTx(tx).insert(...);
  await auditRepo.withTx(tx).insert(...);  // same transaction
});
```

Never open a transaction inside a repository. Never enqueue BullMQ jobs or call external APIs inside a transaction (use the outbox pattern).

## Raw SQL in Migrations

Some database features cannot be expressed in Prisma's schema DSL:

- **GIN indexes with operator classes** (`jsonb_path_ops`, `jsonb_ops`)
- `CREATE INDEX CONCURRENTLY` (cannot run inside a transaction)
- `WITH RECURSIVE` CTEs (query-time, not schema-time)
- Custom `CHECK` constraints with complex expressions
- Partial indexes

### How to add raw SQL to a migration

Prisma migration files are plain SQL in `prisma/migrations/<timestamp>_<name>/migration.sql`. They are **immutable once applied** — Prisma stores a checksum in the `_prisma_migrations` table and will error if an applied file is modified.

**Workflow when raw SQL is needed:**

```bash
# 1. Generate migration file WITHOUT applying
npm run db:migrate -- --name <name> --create-only

# 2. Edit the generated SQL file, add your raw statements
#    e.g. prisma/migrations/<timestamp>_<name>/migration.sql

# 3. Apply the edited migration
npm run db:migrate:deploy
```

**Non-interactive environments** (CI, scripts, Claude Code): `prisma migrate dev` requires a TTY. Use `--create-only` + manual SQL editing + `migrate deploy` instead.

### How Prisma protects raw SQL changes

Once a migration is applied, Prisma records its SHA-256 checksum in `_prisma_migrations`. Future `prisma migrate dev` / `migrate deploy` runs:
- Only generate NEW migration files for NEW schema changes
- Never re-run or overwrite applied migrations
- Error loudly if an applied migration file is modified on disk (checksum mismatch)

Raw SQL added to a migration file before it is applied is completely safe and permanent.

### GIN index pattern used in this project

```sql
-- For JSONB columns (specs on Product and User)
-- jsonb_path_ops: optimal for @> containment queries, smaller than jsonb_ops
CREATE INDEX "Product_specs_gin_idx" ON "Product" USING GIN ("specs" jsonb_path_ops);
CREATE INDEX "User_specs_gin_idx"    ON "User"    USING GIN ("specs" jsonb_path_ops);

-- For array columns (tags on Product)
-- Prisma @@index([tags], type: Gin) generates this automatically
CREATE INDEX "Product_tags_idx" ON "Product" USING GIN ("tags");
```

**Production note:** On tables with existing data, use `CREATE INDEX CONCURRENTLY` to avoid locking. This cannot run inside a transaction block — create a dedicated migration and remove the wrapping `BEGIN/COMMIT`.

## JSONB Columns

| Table | Column | Shape |
|---|---|---|
| `User` | `specs` | Discriminated by role: `{ merchant: {...} }`, `{ verifier: {...} }` |
| `Product` | `specs` | Discriminated by domain: `{ seo?: {...}, shipping?: {...} }` (e-commerce); future domains add their own top-level key |
| `Product` | `media` | Array: `[{ url, altText, mediaType, sortOrder, isPrimary, variantId? }]` |

All JSONB columns are validated at the Zod layer (service boundary) using discriminated unions keyed on the relevant type field. The database stores whatever JSON is given — shape enforcement is application-side.

## Key Invariants

1. **Every business table has `tenantId`.** A query missing a `tenantId` filter is a P0 security bug.
2. **Money is `NUMERIC(18,4)` ↔ `Decimal` (`decimal.js`)** — never `number` or `float`.
3. **Timestamps are `TIMESTAMPTZ`** — stored as UTC, serialized as ISO-8601 at API boundaries.
4. **IDs are UUID v7** for new business entities. Internal FK columns use `BIGINT` auto-increment.
5. **Migrations are forward-only.** A rollback is a new forward migration. Never edit applied migrations.
6. **Audit rows commit in the same transaction as the operation they record.**
